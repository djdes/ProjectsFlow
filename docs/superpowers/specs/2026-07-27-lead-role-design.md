# Роль «Руководитель» (тимлид) — дизайн

**Дата:** 2026-07-27
**Статус:** согласовано, к реализации

## Задача

В пространстве нужен человек, который отвечает за работу команды целиком: у него права
владельца и он в реальном времени знает состояние всех задач всех участников по всем
проектам. Обычные участники продолжают получать уведомления только по своим задачам.

Ключевое ограничение заказчика: **всё, что руководитель видит сверх обычного участника,
приходит лично ему** — в личный чат с ботом и на его почту. Ни одно из этих сообщений не
уходит в общие Telegram-группы.

## Решения

| Вопрос | Решение |
| --- | --- |
| Объём потока | Ключевые события в реальном времени + ежедневная сводка |
| Права | Ровно права владельца |
| Охват | Всё пространство, включая личные «Входящие» участников |
| Почта | Только сводки (реалтайм — в Telegram) |
| Назначение | Выдаёт владелец пространства; руководителей может быть несколько |

## 1. Роль в модели доступа

Роль живёт там же, где остальные — в `workspace_members.role`. Миграция `db/147` расширяет
ENUM значением `lead` (append-only, существующие значения не трогаем).

`ProjectRole` становится `'owner' | 'lead' | 'editor' | 'viewer'`. В матрице прав
(`domain/project/permissions.ts`) `lead` получает тот же уровень, что `owner`, поэтому
`can()` пропускает его во все owner-only действия: удаление проекта, финансы, публичные
ссылки, диспетчер, настройки деплоя, удаление участников, передача владения.

Помимо матрицы роль сравнивается литералом `role === 'owner'` в 16 местах сервера и 19
клиента. Эти места переходят на хелпер `hasOwnerRights(role)` (`role === 'owner' ||
role === 'lead'`).

**Единственное исключение — `requireWorkspaceOwner`**: смена ролей участников остаётся
строго за владельцем. Иначе роль саморазмножается: руководитель назначил бы руководителем
кого угодно и вернул бы себе роль после снятия.

## 2. Реальное время в Telegram

Точка расширения одна — `BroadcastTelegramNotificationByTask`. Сейчас он шлёт событие
единственному получателю, текущему ответственному. Добавляется резолвер аудитории:

```
получатели = ответственный ∪ руководители пространства проекта − актор
```

Руководители читаются через `ProjectMemberRepository.listWorkspaceLeads(workspaceId)`.
Доставка — существующий `SendAgentTelegramNotification` (личный чат пользователя с ботом),
поэтому в группы ничего не попадает by construction.

Новых источников событий не появляется: `status_change`, `task_done`, `task_blocked` и
вопрос агента уже эмитятся при действиях человека и агента. Меняется только аудитория.

Текст руководителю отличается префиксом с именем ответственного — «Олег → «Скелетон
товаров», ScanFlow: в работе → выполнено». Иначе командный поток сливается с его
собственными задачами.

Личные «Входящие» попадают в поток автоматически: у такой задачи есть ответственный и
проект-инбокс, привязанный к тому же пространству.

Приглушение: новый ключ TG-настроек `teamStatusChange` (по умолчанию включён). Он отдельный
от `statusChange`, чтобы руководитель мог выключить командный поток, не теряя уведомлений
по своим задачам. Для не-руководителя ключ не имеет эффекта.

## 3. Личная сводка руководителя

Существующую workspace-рассылку «по ответственным» не трогаем: она умеет уходить в общую
группу, а туда командная аналитика по требованию заказчика попадать не должна.

Вместо этого — отдельная ежедневная сводка, адресованная лично каждому руководителю:
Telegram-DM и письмо. Содержимое: задачи всех участников пространства по проектам,
сгруппированные по ответственным, плюс секция «просрочено» (задачи с истёкшим дедлайном и
незакрытым статусом).

Просрочки живут здесь, а не в реальном времени: отдельного детектора дедлайнов в системе
нет, а пинг на каждую просроченную задачу дал бы всплеск сообщений раз в сутки без пользы.

Расписание — рядом с существующими планировщиками дайджестов, время фиксировано (09:00 MSK,
как утренняя сводка).

## 4. UI

- Дропдаун роли в участниках пространства получает пункт «Руководитель»; пункт виден и
  доступен только владельцу.
- Рядом с именем участника — бейдж «Руководитель».
- В личных Telegram-настройках у руководителя появляется переключатель «Уведомления по всей
  команде».

## 5. Тестирование

- Права: `lead` проходит owner-only действия; `lead` не проходит смену ролей участников.
- Аудитория рассылки: ответственный + руководители, без актора, без дублей; задача из
  личных «Входящих» коллеги попадает руководителю.
- Сводка: адресована лично каждому руководителю, в группы не уходит; секция просрочек
  включает только задачи с истёкшим дедлайном и незавершённым статусом.

## Что осталось за рамками

- Роль на уровне отдельного проекта (сейчас — только на уровне пространства).
- Настраиваемое время личной сводки (фиксировано 09:00 MSK).
- Мгновенные уведомления о просрочке.
