# Фильтр колонки канбана по типу задачи (баги / фичи)

Дата: 2026-08-06
Статус: согласовано, ждёт плана реализации

## Задача

У задач есть тип `feature | bug` (db/153) — бейдж на карточке и группировка во «Входящих».
На доске проекта разделить работу по типу нельзя: колонка показывает всё подряд.

Нужно: у любой колонки нажать кнопку и выбрать, что показывать — только баги, только фичи
или и то и другое.

## Решение

### Модель

Режим фильтра колонки: `all` (по умолчанию) | `bug` | `feature`.

Хранение — `localStorage`, по образцу уже существующего `useDoneSortOrder`
(`client/src/presentation/hooks/useDoneSortOrder.ts`): личная настройка отображения без
серверной синхронизации. Ключ один на проект, значение — JSON-карта «статус колонки → режим»:

```
pf-column-type-filter:<projectId>  →  {"backlog":"bug","done":"feature"}
```

Один ключ вместо ключа на колонку: карта читается и пишется целиком одним хуком, и в
хранилище не остаётся мусора от удалённых кастомных колонок сверх одной записи.

Почему личный, а не в `projects.kanban_settings`: настройки доски — общее состояние проекта,
и фильтр там скрыл бы карточки всей команде. Человек, включивший «только баги» у себя,
не должен прятать фичи у коллег.

### Правило отбора

Задача без типа (`taskType === null`) считается ФИЧЕЙ. Это та же логика, что у
классификатора в compose-промпте («при сомнениях — feature»), и без неё режим «только фичи»
прятал бы почти всё: поле появилось недавно, у большинства задач тип пустой.

```
matchesTypeFilter(task, 'all')     → true
matchesTypeFilter(task, 'bug')     → task.taskType === 'bug'
matchesTypeFilter(task, 'feature') → task.taskType !== 'bug'
```

Чистая функция рядом с `TASK_TYPE_META` в `client/src/domain/task/taskTypeMeta.ts` —
покрывается тестом без React.

### Где применяется

В `KanbanBoard` рядом с существующим `filterTasks`: колонке отдаётся уже отфильтрованный
список. Фильтр колонки и общий фильтр доски (запрос / приоритет / срок / ответственный)
складываются — задача видна, когда проходит оба.

Счётчик задач в шапке колонки показывает ОТФИЛЬТРОВАННОЕ число: иначе «5» над одной
карточкой читается как ошибка.

### UI

В существующем меню колонки «…» (`KanbanColumnMenu`) — секция «Показывать» с тремя пунктами
(«Всё», «Только баги», «Только фичи») и отметкой активного.

Когда режим не `all`, в шапке колонки рядом с названием появляется маленький бейдж «Баги»
или «Фичи» в цвете типа из `TASK_TYPE_META`. Он обязателен: без него отфильтрованная колонка
выглядит так, будто задачи пропали. Клик по бейджу возвращает режим `all`.

### Серверных изменений нет

`taskType` уже в модели задачи и приходит на клиент.

## Границы

**Полка «Вручную» в эту работу не входит.** В дизайне она сначала была включена, но у полки
(`BoardWorkShelf`) нет шапки с меню «…» — только подпись и счётчик. Дать ей фильтр значит
построить там новый элемент управления, а это отдельная работа с собственными решениями по
виду и месту. Полка показывает всё, как сейчас.

**Колонка «На утверждении» и режим наблюдателя тоже вне работы.** Меню «…» сегодня
рендерится только при `canEdit && !approvalColumn` (`KanbanBoard.tsx`, проп `columnMenu`),
поэтому у служебной колонки приёмки и у viewer'а фильтра не будет. Фильтр — это отображение,
а не правка, так что распространить его на наблюдателя логично, но это отдельное изменение
условия рендера меню и его содержимого.

**«Входящие» не трогаем** — там своя поверхность и своя группировка (в том числе уже
существующая группировка по типу).

## Что сознательно не делаем

- Сохранение фильтра в сохранённых вью доски (`ViewFilters`) — это другой механизм с
  серверным хранением и общим доступом.
- Синхронизацию фильтра между устройствами.
- Фильтр по нескольким типам сразу (мультивыбор) — типов всего два, третий режим «всё»
  покрывает объединение.

## Тестирование

- Юнит-тест на `matchesTypeFilter`: задача-баг, задача-фича, задача без типа × три режима
  (9 случаев).
- Ручная проверка на проде: включить «только баги» в одной колонке — в ней остаются баги,
  соседние колонки не меняются; бейдж виден; счётчик совпадает с числом карточек; после
  перезагрузки страницы режим сохраняется; у второго аккаунта доска без изменений.
